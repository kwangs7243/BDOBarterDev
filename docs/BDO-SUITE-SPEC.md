# BDO Suite — 통합 런처 및 연금 제작 관리 시스템

**문서 버전:** 1.0\
**대상:** 로컬 전용 검은사막 웹 애플리케이션\
**기준일:** 2026-10-23\
**수행자:** Codex (고추론 모델)\
**목표:** 기존 물교 프로그램을 보존하면서 상위 런처 및 독립된 연금 제작 관리 앱을 구현하고, 전체 기능을 검증하여 사용할 수 있는 상태로 완성한다.

---

## 0. 코덱스 실행 지침

이 문서는 구현 지시서다. 단순히 계획을 세우거나 TODO를 생성하는 것으로 작업을 종료하지 않는다.

1. 먼저 기존 물교 프로젝트의 디렉터리 구조, 실행 방법, 서버, 프론트엔드 기술, 저장소, 데이터 영속성, 의존성을 조사한다.
2. 기존 아키텍처를 존중하면서 가장 단순하고 안정적인 확장 방식을 선정한다.
3. 구현 전 기존 동작을 확인하고, 변경 후 동일 기능에 대한 회귀 테스트를 수행한다.
4. 연금 앱은 데이터 모델, 계산 엔진, 재고 시스템, UI, 지속성, 테스트까지 구현한다.
5. 각 단계는 테스트 통과 후 다음 단계로 진행하되, 가능한 한 한 작업에서 전체 완성을 목표로 한다.
6. 구현 완료 전에는 사용자에게 임의로 대규모 구조 변경 승인을 요구하지 않는다. 다만 기존 데이터 삭제, 복구 불가능한 마이그레이션, 보안상 중요한 외부 공개 설정은 자동 실행하지 않는다.
7. 사용자가 제공하지 않은 재고 수량이나 검증되지 않은 레시피는 추정하여 확정하지 않는다.
8. 기능 안정성에 영향을 주지 않는 UI·디자인·구현 세부사항은 코덱스가 판단한다.

**최우선 원칙:** 기존 물교 앱의 정상 동작과 사용자 데이터 보존.

# 1. 전체 시스템 아키텍처

## 1.1 디렉터리 구조

목표 구조:

- `BDO/` — 전체 프로젝트 루트
  - `launcher/` — BDO 메인 화면
  - `barter/` — 기존 물교 프로그램
  - `alchemy/` — 신규 연금 프로그램
  - `shared/` — 최소한의 공용 UI 계약 및 내비게이션
  - `data/` — 앱별 영속 데이터 저장 위치 (필요한 경우)
  - `docs/` — 명세, 운영 및 검증 기록

디렉터리 명칭은 현재 프로젝트 환경에 맞게 조정할 수 있다.

물교 프로젝트를 무조건 이동하거나 전체 재작성하지 않는다. 기존 프로젝트 구조 때문에 이동 위험이 크다면 루트에서 물교 프로젝트를 연결하는 방식으로 대체한다.

## 1.2 URL 및 화면

가능하면 기존 로컬 서버와 동일한 Origin을 사용한다.

| 경로 | 화면 |
|---|---|
| `/` | BDO 메인 런처 |
| `/barter` | 기존 물교 프로그램 |
| `/alchemy` | 연금 대시보드 |
| `/alchemy/recipes/:id` | 제작 대상 상세 |
| `/alchemy/inventory` | 연금 재고 |
| `/alchemy/history` | 제작 기록 |
| `/alchemy/settings` | 레시피·데이터 설정 |

라우팅 구현은 기존 프레임워크에 맞춘다. 기존 물교 주소로 직접 접근하는 기능도 유지한다.

### 앱 이동

- 메인 → 물교
- 메인 → 연금
- 물교 → 연금
- 연금 → 물교
- 양쪽 → 메인

모든 이동은 저장되지 않은 중요한 수정 사항을 보호해야 한다.

## 1.3 실행·메모리 격리

물교와 연금은 별도 기능 번들 또는 독립된 페이지로 분리한다.

필수 조건:

- 물교 진입 시 연금 데이터 전체를 메모리에 올리지 않는다.
- 연금 진입 시 물교의 대량 데이터와 화면 컴포넌트를 로드하지 않는다.
- 다른 앱으로 이동하면 이전 앱의 화면 상태, 타이머, 이벤트 리스너, Worker 등을 정리한다.
- 저장된 재고와 제작 기록은 앱을 이동해도 유지한다.
- 영속 저장소와 실행 중 메모리는 분리한다.
- 레시피는 필요한 대상을 중심으로 불러오고 캐싱한다.
- 서버 프로세스가 공용이라도 두 앱의 데이터 세트를 상시 메모리에 유지하지 않는다.

가능하면 코드 분할 및 지연 로딩을 사용한다. 구조가 복잡하다면 독립 페이지 전환으로 격리를 보장해도 된다.

**금지:** 편의를 위해 물교와 연금의 모든 상태를 하나의 전역 Store에 적재하는 설계.

# 3. 레시피 데이터 시스템

## 3.1 데이터 모델

각 아이템은 고유한 안정적 ID를 가진다.

아이템 정보:

- `item_id`
- 한국어 공식 명칭
- 별칭 및 검색어
- 아이템 분류
- 이미지 경로 (선택)
- 제작 가능 여부
- 원재료 / 중간재 / 최종품 구분
- 획득 경로 및 메모

레시피 정보:

- `recipe_id`
- `output_item_id`
- `output_quantity`
- `inputs[]` (아이템 ID와 수량)
- 제작 방식 (주거지 연금, 간이연금, 가공 등)
- 게임 내 요구 숙련 단계
- 제작 산출 방식
- 일반 재료 대체 규칙
- 검증 상태
- 출처 URL
- 검증 일자
- 레시피 데이터 버전

한 아이템에 여러 레시피가 존재할 수 있다.

예: 열망의 향수는 직접 연금 또는 용기의 향수 활용 전환 경로 중 하나를 선택할 수 있다.

## 3.2 제작 수율 분리

모든 레시피를 다음 중 하나로 구분한다.

1. **고정 산출:** 정해진 수량이 나오는 제작
2. **가변 산출:** 연금 숙련 등에 따라 결과가 달라질 수 있는 제작
3. **추가 산출:** 상위 등급 아이템이나 부산물이 함께 생성될 수 있는 제작

가변 산출에서는 실제 결과를 예측해 재고에 추가하지 않는다.

계획 단계의 기본 계산값은 공식적으로 확인된 보장 산출량을 사용한다. 별도 설정에서 사용자가 기대 수율을 입력할 수 있으나, 이는 예상 계산에만 사용한다.

**실제 재고 반영에는 언제나 사용자가 입력한 실제 산출량을 사용한다.**

## 3.3 다중 레시피

한 아이템에 제작 경로가 여러 개라면 다음 기능을 제공한다.

- 기본 제작 경로 선택
- 다른 제작 경로로 변경
- 경로별 요구 재료 비교
- 경로 변경에 따른 부족 재료 재계산
- 특정 목표에서 선택한 레시피 기억

자동 추천은 선택 기능으로 두고, 사용자의 명시적 선택을 우선한다.

## 3.4 대체 재료

같은 이름의 상위 비약이 일반 비약 3개를 대체하는 등, 게임에서 허용하는 치환 규칙을 별도로 모델링한다.

대체 규칙은 해당 레시피에서 허용된 경우에만 사용한다. 게임상 혼합 투입의 허용 여부가 확인되지 않은 경우 자동 혼합을 가정하지 않는다.

사용자는 어떤 재료를 소비할지 확인할 수 있어야 한다.

## 3.5 레시피 검증

검은사막 한국 공식 제작 노트 및 패치 노트를 최우선 출처로 사용한다.

보조 출처는 BDO Codex, 커뮤니티 및 계산기 자료를 활용한다.

특히 2026년 8월 변경 내용을 반영한다.

- 조화의 영약 하위 영약 10개 / 100개 제작식
- 파티형 조화의 영약 10개 / 100개 제작식
- 대량 제작의 촉매제 차이
- 신규 대양 영약
- 열망·관철 향수의 대체 제작 경로
- 녹음 향수·청람 영약
- 통합 흔적 재료 등 과거 레시피 변경 사항

**단순히 10개 제작식의 모든 숫자에 10을 곱해 100개 제작식을 추정해서는 안 된다.** 서로 다른 촉매제와 예외 수량을 정확히 확인한다.

검증되지 않은 레시피는 '검증 필요'로 표시하고 실제 재고 자동 차감에 사용하지 않는다.

초기 필수 제품과 그 모든 하위 제작 경로는 구현 완료 전 검증해야 한다.

# 4. 연금 제작 계산 엔진

## 4.1 핵심 목표

사용자가 만들고 싶은 제품과 수량을 선택하면, 현재 재고를 반영하여 다음 정보를 계산한다.

- 필요한 중간재 총량
- 현재 보유한 중간재
- 부족한 중간재
- 각 중간재를 제작해야 하는 횟수
- 필요한 기초 재료 총량
- 현재 보유한 기초 재료
- 실제 부족한 기초 재료
- 바로 제작 가능한 단계
- 아직 제작할 수 없는 단계
- 최종 목표 진행 상태

계산은 재료의 의존 관계 그래프를 기반으로 한다.

## 4.2 의존 그래프

예시 구조:

조화의 영약\
→ 타락의 영약\
→ 약탈의 비약\
→ 불굴의 오일\
→ 광대의 혈액\
→ 맑은 액체 시약\
→ 기초 재료

이 경로와 별도로 다른 비약이 동일한 맑은 액체 시약을 사용하면 필요량을 합산해야 한다.

동일한 중간재를 서로 다른 두 경로가 필요로 하더라도, 보유 재고를 두 번 사용하는 오류는 발생하면 안 된다.

순환 참조를 발견하면 해당 레시피를 비활성화하고 오류를 보고한다.

## 4.3 재고 우선 계산

**중간재를 보유하고 있다면 해당 중간재를 새로 제작할 필요가 없는 만큼 하위 원재료 요구량도 감소한다.**

계산 절차:

1. 목표 수량 확정
2. 이미 보유한 최종품 반영
3. 부족한 최종품에 필요한 레시피 선택
4. 중간재별 기존 재고 할당
5. 부족한 중간재만 제작 계획에 추가
6. 각 단계의 제작 단위와 수율 반영
7. 최종 부족 원재료 계산
8. 중복 재료를 통합하여 표시

### 계산 예시

가상의 테스트 레시피:

- 최종품 1개 제작에 중간재 A 3개
- 최종품 10개 목표
- 중간재 A 현재고 7개

결과:

- 중간재 A 총 필요량: 30개
- 보유량 반영: 7개
- 추가 필요: 23개

중간재 A 1회 제작에 원재료 B 2개가 필요하고 1개 생산된다면, B는 총 46개 필요하다.

B를 현재 10개 보유했다면 구매 또는 수급 필요량은 36개다.

이는 계산 검증용 가상 예시이며 실제 게임 레시피가 아니다.

## 4.4 배치 제작

레시피마다 실제 산출 단위를 가진다.

예를 들어 10개 또는 100개 단위 제작식은 서로 다른 레시피로 관리한다.

사용자가 25개를 목표로 했을 경우:

- 10개 제작식 3회
- 100개 제작식 1회

등 가능한 계획 중 선택할 수 있어야 한다.

100개 제작식이 언제나 더 효율적인 것은 아니므로, 재료 구성과 남는 결과물을 보여준다.

실제 제작 수량은 선택된 배치 단위에 따라 올림 처리한다.

제작식이 허용하지 않는 소수점 횟수나 임의 분할은 금지한다.

## 4.5 제작 계획의 재계산

재고 수량이나 레시피 경로가 변경되면 현재 계획을 다시 계산한다.

단, 이 과정에서 실제 재고를 차감하거나 이전 제작 기록을 수정해서는 안 된다.

계산 엔진은 가능한 한 순수 함수 형태로 구현하여 UI와 영속 저장 시스템으로부터 분리한다.

# 5. 재고 관리 시스템

## 5.1 재고 종류

세 가지 수치를 엄격하게 구분한다.

- **실제 재고:** 사용자가 인게임에서 확인하거나 제작 기록으로 반영한 수량
- **계획 필요량:** 앞으로 필요한 예상 수량
- **제작 진행 중:** 재료는 차감됐으나 결과물은 아직 등록하지 않은 작업

계획 필요량은 실제 재고가 아니다.

제작 진행 중인 예상 산출물 역시 완료 전에는 실제 재고로 사용할 수 없다.

## 5.2 최초 재고 등록

사용자는 아이템을 검색하여 보유 수량을 입력할 수 있다.

- 아이템명 검색
- 현재 수량
- 저장
- 일괄 입력
- 기존 수량 수정
- 확인 시각 (자동 기록)

미입력 재고와 실제 0개를 구분한다.

미입력 아이템은 '미확인'으로 표시한다. 사용자가 명시적으로 미확인 수량을 0으로 가정하는 계산 모드를 사용할 수는 있으나, 그 설정이 확정 재고로 저장되면 안 된다.

## 5.3 기본 재고 원칙

재고는 영약별로 따로 보관하지 않는다.

모든 연금 제작 목표는 공통 재고를 참조한다.

예를 들어 세월의 비약 500개를 보유했다면 대양의 영약 계획과 청람의 영약 계획은 동일한 500개를 기준으로 계산한다.

동시에 여러 제작 계획이 활성화된 경우 목표별 예약 또는 우선순위 정책을 적용해 같은 수량을 이중으로 할당하지 않는다.

예약은 실제 차감이 아니며 명확하게 표시한다.

# 6. 제작 실행 및 자동 차감

**이번 시스템의 가장 중요한 기능이다.**

## 6.1 제작 시작

사용자가 중간재 또는 최종품을 선택하고 제작 횟수를 입력한다.

예:

- 약탈의 비약
- 200회 제작

시작 전 화면:

- 필요한 재료
- 재료별 현재 보유량
- 차감될 수량
- 부족 여부
- 예상 결과물 (참고용)
- 제작 방식

사용자가 **'제작 시작'** 버튼을 누르면 다음 동작을 하나의 원자적 트랜잭션으로 수행한다.

1. 최신 재고 재확인
2. 재료 소모 가능 여부 검증
3. 필요한 재료 차감
4. 제작 진행 중 작업 생성
5. 재고 변경 이력 저장
6. 변경 상태 영속 저장

차감이 일부만 완료되는 상태는 허용하지 않는다.

## 6.2 제작 완료

사용자가 실제 게임에서 제작을 마치면 결과를 입력한다.

일반 비약과 상위 비약이 함께 나온다면 각각 별도 입력한다.

예:

- 일반 약탈의 비약 480개
- 강력한 약탈의 비약 18개

이는 UI 동작 설명용 가상 수량이다.

'제작 완료'를 누르면:

1. 제작 작업을 조회한다.
2. 입력된 실제 산출 수량을 검증한다.
3. 해당 결과물들을 실제 재고에 추가한다.
4. 작업 상태를 완료로 변경한다.
5. 제작 기록에 입력·출력 수량을 저장한다.
6. 모든 활성 제작 계획의 진행도를 갱신한다.

완료 버튼 중복 클릭으로 재고가 이중 추가되면 안 된다.

## 6.3 제작 취소와 오류 복구

다음 상황을 지원한다.

- 제작 시작 전 취소: 아무것도 차감하지 않음
- 제작 시작 후 실제로 제작하지 않은 상태에서 취소: 재료 원상 복구
- 일부 제작 진행 후 중단: 실제 수행한 회차와 결과물만 확정 반영하고 미사용 재료 반환
- 제작 완료 결과 입력 오류: 정정 기록으로 처리
- 앱 종료 후 재실행: 진행 중 작업 복구

정정이나 취소 때문에 재고가 음수가 되거나 이후 작업의 소모 기록을 훼손하는 경우 자동 롤백하지 않는다. 충돌을 표시하고 사용자 확인 기반의 보정 거래를 사용한다.

모든 기록에는 고유 트랜잭션 ID를 부여한다.

## 6.4 수동 재고 변경

다음 기능을 지원한다.

- 채집/노드 수급으로 수량 추가
- 거래소 구매로 수량 추가
- 게임에서 사용하여 수량 차감
- 창고 실사 결과로 절대 수량 정정

각 변경에는 유형과 시간을 남긴다.

# 7. 진행률과 제작 대시보드

## 7.1 제작 목표 생성

사용자가 목표 아이템과 목표 수량을 등록한다.

기본적으로 **'최종적으로 몇 개 보유할 것인가'**를 기준으로 한다.

필요하면 **'현재 보유분과 별도로 몇 개를 추가 제작할 것인가'** 모드도 선택할 수 있다.

두 모드는 명확하게 구분한다.

예:

조화의 영약 100개 확보

## 7.2 진행 상태 표시

다음 세 가지는 별도로 보여준다.

1. **최종 목표 달성률:** 실제 확보한 최종품 수량 / 목표 수량
2. **재료 준비 현황:** 각 제작 단계의 필요량, 보유량, 부족량
3. **제작 단계 진행 상태:** 준비 가능, 재료 부족, 제작 중, 제작 완료

중간재를 만들었다고 최종품이 완성된 것처럼 표시해서는 안 된다.

전체 제작 준비도를 별도 지표로 제공할 경우에는 배치 단위, 중간재와 원재료의 중복 가치, 다른 목표에 예약된 재고를 고려해야 한다. 정확하게 계산되지 않는 비율을 임의의 진행률로 표시하지 않는다.

## 7.3 추천 대시보드 구성

### 상단

- 제작 대상
- 목표 수량
- 현재 보유량
- 부족 수량
- 최종 목표 달성률
- 제작 가능한 다음 작업

### 중앙 왼쪽

단계별 제작 트리.

각 아이템에:

- 아이콘 / 이름
- 필요 수량
- 보유 수량
- 부족 수량
- 제작 횟수
- 준비 상태
- 펼치기 / 접기

### 중앙 오른쪽

선택한 제작 단계의 상세 패널.

- 연금 재료
- 제작 횟수 입력
- 차감 미리보기
- 제작 시작
- 실제 산출량 입력
- 제작 완료

### 하단

통합 부족 재료 리스트.

- 부족 원재료
- 부족 수량
- 수급 방식
- 보유 확인 필요 항목
- 클립보드 복사 기능

## 7.4 필터 및 사용성

- 필요한 재료만 표시
- 부족한 재료만 표시
- 이미 준비된 항목 숨기기
- 제작 가능한 항목만 표시
- 최하위 원재료만 표시
- 중간재까지 전체 표시
- 제작 단계별 접기 / 펼치기
- 이름 검색

대량의 조화의 영약 트리는 처음부터 모든 노드를 화면에 렌더링하지 않는다. 단계별 지연 렌더링을 사용한다.

# 8. 재고 및 제작 데이터 영속성

로컬 앱은 브라우저 새로고침, 앱 종료, 서버 재시작에도 데이터를 유지해야 한다.

현재 서버 구조를 확인하여 다음 중 적절한 방식을 택한다.

- 기존 서버가 데이터베이스 사용 가능: SQLite 우선 검토
- 순수 브라우저 기반: IndexedDB 등 구조화된 영속 저장소
- 기존 앱의 안정적인 저장 방식이 있는 경우: 해당 방식을 검토하되 앱별 데이터 영역 분리

대규모 재고 및 제작 이력 전체를 단순 localStorage 하나에 계속 덮어쓰는 방식은 피한다.

### 저장할 데이터

- 연금 재고
- 제작 목표
- 사용자별 레시피 선택
- 진행 중 제작
- 제작 완료 기록
- 재고 변경 원장
- 레시피 데이터 버전
- UI 설정

### 복구 기능

- 전체 데이터 내보내기(JSON)
- 백업 가져오기
- 스키마 버전 확인
- 가져오기 전 검증 및 미리보기
- 기존 데이터 덮어쓰기 전 백업
- 앱별 데이터 분리

물교 데이터는 이 작업의 대상이 아니다.

운영 Google Sheets와의 자동 동기화는 초기 범위에서 제외한다. 연금 앱의 재고는 로컬 제작 관리를 위한 값이며, 별도의 운영 시트와 자동으로 일치한다고 표시하지 않는다.

추후 동기화 기능을 만들 경우 충돌 해결 규칙과 사용자 확인을 별도로 설계한다.

# 9. 디자인 시스템

## 9.1 디자인 컨셉

**Black & Gold Alchemy Workshop**

검은사막의 연금술 작업실, 고급 판타지 제작 메뉴, 오래된 연금 기록서를 현대적인 관리 대시보드로 해석한다.

화려한 게임 UI보다 실제 제작 중 빠르게 읽고 조작할 수 있는 디자인을 우선한다.

### 권장 색상

- 메인 배경: `#0B0E12`
- 카드 배경: `#141922`
- 강조 금색: `#C8A75A`
- 밝은 금색: `#E6D09A`
- 기본 텍스트: `#E8E4DC`
- 보조 텍스트: `#9CA3AD`
- 상태 색상: 의미에 맞는 절제된 색상

### 분위기

- 어두운 금속 재질
- 절제된 금색 테두리
- 연금술 인장 및 원형 문양
- 아이템 중심의 작은 카드
- 섬세하지만 과하지 않은 애니메이션
- 높은 텍스트 대비
- 촘촘하고 정돈된 정보 밀도

가능하면 실제 검은사막 아이템 아이콘을 사용하되 저작권, 접근성 및 사용 가능 여부를 확인한다. 불확실하다면 자체 아이콘 체계로 대체한다.

## 9.2 메인 런처

통일된 BDO 스타일의 메인 화면을 제작한다.

진입 카드:

- **물교** — 기존 물교 프로그램으로 이동
- **연금** — 신규 연금 제작 관리로 이동

물교 앱 내부 디자인 전체를 강제로 교체하지 않는다.

기존 프로그램과 연금 프로그램은 각자의 디자인을 유지하되 이동 버튼과 헤더의 통일감은 확보한다.

## 9.3 UX

- 주요 동작은 2~3번 이내의 클릭으로 접근
- 숫자 입력은 키보드 중심 작업에 최적화
- 제작 완료 입력이 빠르고 명확해야 함
- 잘못된 숫자 입력 방지
- 중요 동작에 확인 및 취소 제공
- 대량 숫자 천 단위 구분
- 반응형 화면 지원
- 마우스뿐 아니라 키보드로도 주요 동작 접근 가능

초기 완성 범위를 불필요하게 확대하지 않는다.

- 다중 사용자 동기화
- Google Sheets 실시간 재고 동기화

- 자동 아이템 수집
- 화면 OCR
- 채집 노드 최적화 엔진

이 기능들은 확장 가능성을 남기되 초기 완성의 필수 조건으로 사용하지 않는다.

# 11. 단계별 구현 지시

## Phase 0 — 기존 프로젝트 조사

- 저장소 전체 구조 분석
- 물교 앱 실행 및 현재 기능 검증
- 데이터 저장 경로 확인
- 서버·라우팅 구조 분석
- 테스트 도구 확인
- 백업 및 변경 범위 확정
- 연금 모듈의 독립 경계 결정

**통과 조건:** 기존 앱을 실행할 수 있고, 현재 데이터와 실행 경로를 보존하는 확장 설계가 확정됨.

## Phase 1 — 런처 및 독립 모듈

- BDO 루트 구축
- 물교 앱 연결
- 연금 앱 진입점 생성
- 앱 간 이동 구현
- 지연 로딩
- 이동 시 자원 해제

**통과 조건:** 양쪽 앱을 오갈 수 있고, 기존 물교 기능에 회귀 문제가 없음.

## Phase 2 — 레시피 데이터베이스

- 아이템 스키마 구현
- 레시피 및 제작 경로 스키마 구현
- 초기 필수 제작품 등록
- 모든 하위 레시피 연결
- 출처·버전·검증 상태 저장
- 순환 참조 검사
- 누락된 제작 재료 검사

**통과 조건:** 지원하는 모든 최종품이 유효한 기초 재료 또는 외부 수급 재료까지 전개됨.

## Phase 3 — 계산 엔진

- 제작 목표 계산
- 레시피 트리 확장
- 중간재 재고 우선 사용
- 다중 경로 선택
- 수율 및 배치 계산
- 중복 재료 합산
- 부족 재료 계산
- 다중 목표 재고 중복 할당 방지
- 단위 테스트 구현

**통과 조건:** 알려진 테스트 데이터에서 계산 결과가 정확하고 재고를 변경하지 않음.

## Phase 4 — 재고 및 제작 트랜잭션

- 재고 저장
- 수동 수량 입력
- 제작 시작 자동 차감
- 제작 완료 실제 결과 추가
- 부분 완료
- 취소 및 원상 복구
- 작업 이력
- 중복 제출 방지
- 앱 재시작 복구
- 데이터 백업

**통과 조건:** 제작 작업의 시작·완료·취소·복구 시 모든 재고가 일치함.

## Phase 5 — UI/UX

- 메인 런처
- 제작품 카탈로그
- 제작 목표 화면

# 13. 최종 완료 조건

다음 조건이 모두 충족되어야 완료로 인정한다.

- 기존 물교 앱이 정상 실행된다.
- 기존 물교 데이터가 보존된다.
- BDO 메인 런처가 동작한다.
- 물교와 연금 사이를 이동할 수 있다.
- 화면 이동 시 불필요한 앱 데이터를 메모리에 상주시켜 두지 않는다.
- 초기 대상 영약 및 향수의 전체 제작 트리가 동작한다.
- 보유 중간재가 부족 원재료 계산에 정확히 반영된다.
- 실제 제작 회차를 기록하고 입력 재료를 자동 차감한다.
- 실제 산출량 입력 후 재고가 정확히 증가한다.
- 여러 목표 사이에 재고 중복 사용이 없다.
- 진행률과 제작 상태가 실제 재고에 기반해 갱신된다.
- 새로고침, 재시작, 취소, 정정에도 데이터가 일치한다.
- 모든 필수 테스트가 통과한다.
- 레시피 데이터에 출처 및 검증 상태가 존재한다.
- UI가 완성되어 실사용 가능하다.
- 실행 및 백업 방법이 문서화되어 있다.

## 최종 보고 형식

구현 완료 후 다음 사항을 간결하게 보고한다.

1. 생성 또는 수정한 주요 디렉터리와 파일
2. 시스템 아키텍처 및 선택 이유
3. 구현한 기능
4. 실제 등록된 레시피 수, 지원 제작품 및 검증 상태
5. 테스트 실행 결과와 통과 여부
6. 성능 및 메모리 격리 검증 결과
7. 실행 방법
8. 남은 제한 사항 또는 검증되지 않은 항목

검증하지 못한 기능을 완료했다고 보고하지 않는다.
